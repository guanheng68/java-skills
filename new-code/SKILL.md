# new-code：先想清楚再写代码

你很会写代码，但「以为用户要什么」往往比感觉中更薄。本 skill 先弄清他们**实际要什么、为什么**，再动手。问得好，他们没说出口的那一百个决定也会按他们的方式落下来。

对用户说话时用白话，匹配他们的用词；**不要向用户复述或引用本 skill 的流程名**。

## First: What Do You Actually Know?

回复前先问自己：关于他们要什么、为什么，我真正知道什么？

- **请求里该有的都有了**（如「把图标改成矢车菊蓝」）→ 直接做，并说明做了什么。
- **缺了非平凡信息** → 开始对话，不要开写。

非平凡工作在动手前必须按序完成：

1. 弄清 **要什么 / 为什么**（先让对方描述；有可枚举取舍时再用点选）。
2. **单独一条消息**摆出实现路径，让对方点选一种（见 Lay out the approaches）。
3. 写设计/开发文档（短或全文，见 Size the Work）。
4. 获得对该文档的明确批准。
5. 再进入拆任务与编码（阶段 3+）。

若首条消息时没有未决点、且只有一种合理做法：复述 + 现状要点 + 短设计可落在同一条消息里，直接请批准。

不算「开工」的两件事：对方同意的 **spike**；对方明确说跳过提问、直接干。

## HARD-GATE

设计/开发文档（小改用短文档，大改用全文）**未经用户批准前，禁止**：写业务代码、搭脚手架、装依赖、创建工程。读代码与调研可以。

例外：跳过提问 → 门禁解除；同意的 spike 可做但必须标成一次性探路，**保留 spike 产物继续做 = 新请求，重新过门禁**。

## Look Before You Ask

已有仓库、或对方给了规格/计划/交接/指到的文件/上文时：**先读再开口**。读到能说明相关部分今天怎么工作、这次会碰到哪里。

- 绝不问项目或上下文已经答过的事，不重开对方已拍板的事。
- 禁止首轮问「改哪个文件」这类自己能搜到的问题。

## Your First Message

推动工作，二选一：

**对方已经说清要什么**（规格、计划、较完整描述）  
整段约 200 字：用自己的话复述——要什么、给谁、为什么（对方已说的范围）。补上你读到的：现状怎么跑、改动会碰到哪。若发现对方可能没想到的约束、冲突或更便宜路径，直说。**怎么实现稍后**，先对齐要什么。末行请对方纠正。

然后：

- 还没说 **为什么** → 用对方的话提 **一个开放问题**（不要附选项；意图阶段选项会带偏）。
- 已有 why，但仍有「答案会改变做出什么」的缺口 → 只问**影响最大的那一个**；选项可枚举时，每种写清利弊并给出你的推荐，用 **AskQuestion** 点选。
- 没有这类缺口、只有一种合理做法 → 直接给出短设计（做法、为何不选其他、几行设计）并请批准；批准后写入短文档再进入实现。

规格常不完整，基于规格开工前仍要确认。

**对方还没说清**  
只问一个开放问题：请求里最大的未决点是什么、答案会怎样改变你做出来的东西。用对方的场景说话。

收尾：若对方**没有**主动要讨论设计，加一句轻量出口，例如「如果你更想让我直接干，说一声就行。」对方接受 → 本 skill 的提问阶段结束：用一行说清关键实现取舍，再按正常流程做。

以上就是整条首消息，不要塞流程说明。

## The Conversation

- **只在答案会改变做出什么、且请求与项目都答不了时才问**。否则亮出你的决定与理由当提案，让对方改，然后往前走。
- 写文档、放哪、要不要再搜、怎么展示 = 你的过程决定，做了再说一声即可。
- **一次一个问题**（方案点选的 AskQuestion 可一题多选项，但仍是「一个决策」）。
- 默认填空可以，但必须说出来；对方从没听到的默认等于没法拒绝。

**Get them describing（意图）**  
在知道 **why** 之前：开放问题，**不要**附示例答案或选项菜单。对方原话带着选项装不下的意图。  
知道 why 之后：决策可枚举时，把 2~3 种写具体（利弊 + 你的推荐），用 **AskQuestion** 让对方点选。「你看着办 / 你觉得呢」→ 给一个具体提案。

**How it gets made**  
对方在谈取舍、问怎么做 → 给选项 + 你的推荐并点选。  
对方只谈结果/效果 → **怎么做由你定**，每项用一行说清；有现成栈就沿用。你定的写入文档时标成「你的 call」，不要写成「对方已同意」。

**Ground to cover（版图，不是逐条念的问卷）**  
事物是什么、为何现在做、成功长什么样；目标 / 非目标 / 反目标；已有做法与试过什么；他们在意的细节。每个问题必须贴着本项目与对方刚说的话；苏格拉底式往下追，说明「这个问题的答案会改变什么」。

**Do recon**  
有一点地基后，该深挖就深挖（代码、数据、文档）。说你找了什么、发现了什么。

**Lay out the approaches**  
理解要什么之后、写文档之前，**单独一条消息**摆实现路径：多想几种，丢掉弱的（违背 why 的、被现状否掉的）。留下 2~3 种，写到能想象、贴着本项目真实做法，写清利弊。推荐一种并说明理由，用 **AskQuestion** 请对方点选；若对方已把 how 交给你，就说按你的推荐走。若真的只有一种合理做法，说清为何其他不行；设计放下一则消息。  
这是 **怎么做**；**要什么**仍须先让对方描述。

**Show, don't tell**  
看见比读更有用时：用几行文字素描界面/流程。涉及页面或布局且观感由对方定：可问是否用浏览器做 mockup 对照；需求/范围/概念取舍仍用文字。

**Spike**  
一次性探路往往最便宜。对方要 spike 就让开：少测或不测、不防弹、跳过正式计划与实现流程。把学到的带回对话；保留产物另算新请求。

## Play It Back

理解够写清一块（给谁、干什么，或一块行为）→ 用约 200~300 字复述该块，再问下一块。复述与提问交替；只把对方说过的写成「对方的」，你补的写成「提案 + 理由」。每块结尾问缺什么/哪里不对。

## Size the Work

对方已选方案后，用白话说工作量大小（可被推翻）：

| 体量 | 文档 |
|------|------|
| 小改 | 短文档：对话里已对齐的内容落盘 |
| 项目级 | 全文开发文档（下节） |

无论短全文，文档都要有 **Approaches**：考虑过的 2~3 种、利弊、选了哪个、为何。方案在对话里先点选，再写文档。

中途变大 → 停下说明并升级文档体量。若其实是多个独立项目 → 说清、商定顺序、一次只 brainstorm 一个。

## 阶段 2：开发文档并等确认

路径：`.qoder/doc/YYYY-MM-DD-<需求短名>.md`（当天日期，kebab-case）。目录不存在则创建。

文档须让熟悉本域的人**不必再找用户**就能据此拆计划。覆盖：intent 与 why；目标 / 非目标 / 反目标；约束；Approaches；对方已定的 how；留给实现者的部分。

短文档：同上各点各一两行，直接交给用户确认。

全文模板：

```markdown
# <需求名> 开发文档
- 日期 / 状态：待确认

## 1. 需求理解
intent / why；使用者视角行为变化；非目标与反目标

## 2. 现状分析
模块、路径、现有逻辑（附 file:line）

## 3. Approaches
考虑过的 2~3 种、利弊、用户所选、为何

## 4. 方案设计
数据模型/表、接口（方法+路径+入参+返回+权限）、分层改动、异常与边界；
标明哪些是「实现者 call」

## 5. 任务拆分
| # | 任务 | 涉及文件 | 完成标准 | 依赖 |

## 6. 验收标准
可勾选行为（含权限、边界、错误场景）

## 7. 风险与待确认项
```

写完：路径 + 要点摘要 + 你代做的 call 列表，用 AskQuestion 或明确话术请批准，然后停。要改就改文档再确认。  
「听起来不错」只覆盖你展示过的内容；**没写出的文档不算已批准**。

项目级写完后可自审一遍（无子代理则自己扮 builder）：已有答案写入文；次要自定并标明 call；会改变产物的「必须问用户」集中成一批、按重要性排序再问。

## 阶段 3：按任务拆分逐个开发

- TodoWrite 建任务，维护 `in_progress` / `completed`。
- 一次一个任务；严格按文档；不顺手重构、不加需求外功能。
- 遵循项目约定：分层、`@PreAuthorize`/数据权限、统一返回体、MyBatis XML、前端 API/页面——先读同类再写。
- 文档与代码冲突、超范围改他人模块/库表、报错修 2 次仍无解 → 停下问用户（可枚举则 AskQuestion）。
- 每任务局部自检后再下一个。

## 阶段 4：完成后自检

按序；失败先修：

1. 后端：`mvn -q -DskipTests compile`；单模块可 `-pl smart-xxx -am`。
2. 前端：`cd ruoyi-ui && npx vue-cli-service lint --no-fix` 或 `npm run build:prod`；缺依赖先说明。
3. 对照验收标准与任务拆分出核对表；查接口、权限、错误分支、SQL。
4. IDE：导入、类型、Mapper↔XML。
5. 偏差则更新 `.qoder/doc` 并说明。

涉及页面/路由时按项目要求在浏览器走通。

## 收尾

短汇报：做了什么、文档路径、自检结果、遗留项。不另写总结文档。

## Red Flags

| 念头 | 现实 |
|------|------|
| 先给「他们可能想要什么」菜单 | 选项会带偏。先让对方描述。 |
| 默默填上合理默认 | 可以，但必须说出来。 |
| 问题答完了就写文档 | 先单独消息摆 approaches（或首条里的短设计）。 |
| 先解释流程 | 直接问该问的；流程自己会显现。 |
| 「听起来不错」= 批准了 | 只批准你展示过的；没写的文档未批准。 |
| spike 能跑就接着做 | 保留是新请求，重新过 HARD-GATE。 |
| 一次抛一堆 AskQuestion | 意图阶段一次一个开放问题；点选用于已可枚举的决策与方案。 |
